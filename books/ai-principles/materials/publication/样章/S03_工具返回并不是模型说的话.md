# 工具返回，并不是模型说的话

> 连续性试样：C37接页—C38的轨迹和学习—C39的执行问题。不假装这是初学第一章，也不假装本包已经训练了真实语言模型。正式书中必须先完成相应语言模型训练；此处前页重建本段实际使用的概率、损失和生成接口。

## 前页：模型给出字符串，宿主决定如何解释它

<a id="s03-p01"></a>
我们现在处理的是一个已有语言模型。给定前缀 \(h\)，它为下一个token给出分布；连续生成 \(a_1,\ldots,a_m\) 的条件概率是
\[
p_\theta(a\mid h)=\prod_{j=1}^m p_\theta(a_j\mid h,a_{<j}).
\]
把可信示范作为目标时，可以最小化对应的负对数概率，使用已有反向传播更新 \(\theta\)。实际作答则是从这些分布选择token，再把选择结果接进前缀。仅仅生成一次，没有执行参数更新。这些关系不因我们接下来把一段文字称为“工具请求”而改变。

<a id="s03-p02"></a>
假设用户问 \(12\times13\)。模型可能直接回答，也可能生成一个结构化请求：`{"tool":"multiply","args":[12,13]}`。宿主程序检查名称和参数，在允许的范围内执行乘法，再得到156。这里完成乘法的是工具，生成请求的是模型；模型本身没有因为写出了JSON就执行了Python。把结果提供给下一次模型调用后，它才能继续利用这条新信息组织回答。

## 核心：一次交互包含两种不同来源的内容

<a id="s03-p03"></a>
这样的记录至少含四段：用户问题、模型请求、工具返回、模型最终回答。读起来像一串对话，来源却不同。用户和工具提供的文字是模型遇到的条件，不是这一次由模型采样出的动作。这个区别平时容易被文本格式盖住，一到训练便会改变我们到底在教什么。

<a id="s03-p04"></a>
外部工具与语言生成的结合并非本书临时发明。Toolformer研究的一个明确对象，就是让已有语言模型学习何时调用API、给出什么参数，以及如何利用结果继续预测。这个公开问题足以说明：会用工具不只是宿主把接口接通，还包含需要学习的行为；但该研究不是随机空白模型从无到有的完整能力起源，也没有替任意工具提供执行安全保证。下面的轨迹和训练目标是本书自己的示范安排，不冒称复刻其筛选算法。[W10]

<a id="s03-p05"></a>
先选择监督学习这条路线。准备一条经过检查的交互示范，目标是学习模型在其中应该做的两个动作：产生正确请求；看见真实返回以后正确回答。我们暂不要求它模仿工具生成156的过程。设整段序列的每个位置有来源标签，模型应生成的位置取 \(m_t=1\)，用户及工具返回位置取 \(m_t=0\)。相应目标可以写为
\[
L(\theta)=-\frac{1}{\sum_t m_t}\sum_t m_t\log p_\theta(x_t\mid x_{<t}).
\]
前缀仍然包括用户问题与工具结果。把某个位置从预测损失中去掉，不等于把它从输入中删除；后续回答依然可以依赖它，其计算也可以承接回答损失的梯度。

<a id="s03-p06"></a>
为什么要作这个选择？我们想从示范里学习“何时、怎样请求，以及怎样利用观察”，而不想因为工具结果有固定拼写，就让平均损失被许多容易预测的工具字符掩盖。它也使模型动作的质量能够单独检查。不过，对整段交互做普通语言建模也是另一种可以研究的训练目标，不能称其数学上非法。需要区分的是：**模仿整份记录的文字分布**与**学习自己负责的动作**，并明确本章采用后者。

<a id="s03-p07"></a>
还可以只检查交互中的生成概率，不必在这里提前调用策略更新算法。若一次交互是请求 \(a\)、环境返回 \(o\)、最终回答 \(b\)，由模型负责的两个生成因子的对数之和为
\[
\log p_\theta(a\mid h)+\log p_\theta(b\mid h,a,o).
\]
环境怎样返回 \(o\) 的概率，属于另一个过程；不能把 \(\log p_\theta(o\mid h,a)\) 当作这次模型曾经采样的行为加进去。这里用的仍是前页已有的条件概率与乘积取对数。将来使用基于回报的参数更新时，也必须保留这种来源区别；此处没有借那个未来算法解释当前计算。

<a id="s03-p08"></a>
处理token时还会出现一个具体的错位。模型在位置 \(i\) 的输出预测位置 \(i+1\)，所以本次输出是否计入损失，应当看**目标位置**的来源，而不是当前位置输入的来源。

```python
def action_targets(token_ids, produced_by_model):
    if len(token_ids) != len(produced_by_model):
        raise ValueError("each token needs an origin label")
    if len(token_ids) < 2:
        raise ValueError("at least two tokens are needed for one target")
    inputs = token_ids[:-1]
    targets = token_ids[1:]
    loss_mask = produced_by_model[1:]
    return inputs, targets, loss_mask
```

`produced_by_model`与整个token序列等长。切去其第一个元素，是让它跟预测目标对齐。实际工程还要明确角色标记、工具名、参数、边界token哪些由模型生成，哪些由宿主插入，不能凭“这一段大致是assistant”猜测所有位置。

## 不是只让它多调用工具

<a id="s03-p09"></a>
一种偷懒的训练会把“出现了调用”作为成功，于是模型遇见任何问题都先调用。这不能代表会用工具。示范和评估应当包含可以直接回答、确需工具、参数不合法、工具失败，以及返回结果改变时答案应该随之改变的情况。否则它可能只学会请求的外形，也可能记住156而完全忽略工具返回。只改返回但不改用户问题，就是区分“利用了观察”与“照旧回答”的一种检查；正式任务中还要保证这种反事实返回与测试目的相容，不把错误工具结果无条件当真实答案。

<a id="s03-p10"></a>
这时，一条工具学习任务的边界已经比较清楚：目标示范来自谁，请求怎样被分词，动作位置怎样计分，工具结果怎样进入前缀，以及怎样在未见任务中检查选择与结果利用。把这些接到自己已有的模型，才是相应的学习实验。我们这里验证了序列对齐与职责划分，没有以一份乘法记录宣布模型已获得通用工具能力；正式建设仍要使用真实模型、变化任务和独立结果。

## 后页：请求正确，任务仍可能没有可靠完成

<a id="s03-p11"></a>
乘法是只读计算，重复执行通常不改变外部世界。现在把工具换成“给文档追加一段内容”。工具已经追加成功，返回消息却在网络中丢失。模型看到的只是超时：工具根本没执行和工具执行但回执丢失，两种世界此时可能给出相同观察。再多想几轮，不会自动取得那条未收到的事实。

<a id="s03-p12"></a>
如果宿主把重试视为一个全新操作，文档可能被追加两次。为使同一次逻辑请求可以被识别，我们需要稳定的操作身份；为判断做过什么，需要可核对的执行结果；为避免修改已变化的文档，还可能需要版本条件。具体工具若不支持查询或去重，宿主不能许诺任意远端副作用“恰好一次”。下一章从这两种不可区分的执行状态出发研究Harness，而不是再给模型一条“请谨慎”的提示词。这与本章学习工具策略相接，却不是同一个参数训练问题。

## 自行检查

若把工具返回的所有位置都从输入中删掉，仅保留它们的loss mask为0，模型最终回答的任务有何变化？若训练库含有工具失败记录，是否应该把失败描述本身当作模型错误答案惩罚？若一个工具请求在生成格式上完全正确，能否据此认定允许执行？

**解析。** 删除输入切断了观察到回答的条件关系，不能再声称模型使用了该返回。工具失败文字是环境反馈，本身不等于模型动作错误；需要看请求是否合适、收到失败后如何继续。格式合法与授权/作用域是两项条件，宿主仍需检查权限和副作用边界。
