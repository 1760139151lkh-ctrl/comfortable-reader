# 从收到文件到真正交付

这份流程用于首次普通请求，不需要用户追加“别用图片”“别丢内容”等提醒。关卡是 agent 的工作步骤，不是要求用户逐次批准。

## 关卡一：确定实际软件和书库

1. 识别用户正在用的 `舒适阅读书库` 安装程序和窗口，而不是只按相同窗口标题猜测。
2. 读取已登记书库。Windows 的共享登记文件是 `%APPDATA%\ComfortableReader\library-roots.json`；安装版也有自己的书目/进度状态。
3. 将用户当前应用登记根目录与实际 Calibre `metadata.db`、书籍路径相互核对。没有跨机器通用的默认库路径；找不到就先说明，不能猜目录。
4. 记录书目基线与目标书是否已存在，选一部正常书观察主题、字号、段落、公式和多页行为。不能把另一个失败导入稿当作“正常参考书”。
5. 工作稿和备份放在未登记的工作目录，避免被自动扫描成多本书。不要以“找不到库”为由创建新的空 Calibre 目录。

**通过依据**：安装程序、已登记根目录、Calibre 记录与实际 EPUB 文件对应一致。历史案例的“9 本书”“13 号书”不是固定配置。

## 关卡二：确定输入和输出范围

- 用户提供本地文件时，以该文件为权威源。保留源字节与哈希。
- 用户指定旧对话作反面教材时，先提取其中的实际抱怨，转成验收项；但即使未给旧对话，也要执行本技能已有的质量检查。
- 用户明确“完全重做”时，从原稿建立独立工作稿。失败 EPUB 的样式、段落和裁图不得继续作为正文基础。
- 用户只要求总结、审查或修改技能时，不继续旧导入任务，不沿用旧目标的写库授权。
- 若任务只是现成 EPUB 入库，先验证是否已经可读，保留已存在的字体、资源、目录和 spine，不为“使用技能”而重复抽取正文。

## 关卡三：样章必须能暴露错误

PDF 按 `pdf-reconstruction.md` 选样。普通结构化文字检查其真实包含的标题、列表、代码、表格、数学等类型，不必制造并不存在的复杂内容。

看这些具体现象，不只看“页面出来了”：

- 一个正常句子是否因为斜体/换字体变成几段？页尾句子是否在下一原页断裂？
- 图是否完整？长图注是否以可读字号续排且归属清楚？表格标题是否正对正确列？空格有没有保留？长算法是否保留行号、缩进、注释和分支范围？
- 公式的指数、下标、帽子、上下限、标点和编号是否存在且位置正确？
- 是否有反斜杠命令、随机英文、占位文字、空白图片或混乱的数学碎片？
- 正文计算字号是否随 3/10 页模式变化？不要只读取下拉菜单值；检查实际显示与字体。
- 小样不足十页时，不能据此判断十个实际页面是否都完整。扩大测试内容或采用足够长的合成结构样本。

常规文字也需要可读性判断：合理的行长、连续段落、协调的数学基线、与阅读器主题相符的颜色，以及没有普遍一两个词的英文窄条。

修规则后重做同一组样章，再开始全量处理。只挑最容易的部分成功，不代表方法可用于整书。

## 关卡四：最终文件的证据

分别完成以下检查，不能互相替代：

| 证据层 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 源文件 SHA-256 与嵌入字节比较 | 原输入能原样恢复 | 可见正文正确或完整 |
| 源单位到输出的映射与差异处理 | 内容去向明确、已知遗漏/重复已处理 | 光靠数量不能证明读序与公式语义 |
| ZIP/XML/资源/链接/MathML 审计 | 包结构有效、资源可达、没有已检测到的语法泄漏 | 不保证识别准确、边线可见或阅读舒服 |
| 实际渲染对照 | 被检查部分的显示和语义符合源稿 | 小样、旧版本或模拟器不能证明最终安装版整书 |

运行只读审计：

```powershell
python <skill-dir>\scripts\persist_epub.py <final.epub> --report <audit.json>
```

需要核对内嵌原文件时加 `--source <original> --source-entry <exact-zip-member>`。先列 EPUB 内容查清条目名，不要猜。构建脚本的 `epub.source_entry` 会报告它写入的原稿条目。

处理所有未决问题后，为**当前最终字节**写技术验收记录。下面是未完成记录的模板，不能直接改成通过而不执行检查：

```json
{
  "epub_sha256": "从当前最终文件实际计算的哈希",
  "source_review": {"status": "pending", "method": "verbatim_source|unchanged_epub|pdf_reconstruction", "byte_equal": false, "source_sha256": "", "coverage_report": "", "evidence": [{"kind": "bytes/coverage", "location": "file or report", "result": "what was checked"}]},
  "render_review": {"status": "pending", "evidence": [{"kind": "visual/installed-app", "location": "book/page/mode", "result": "what was observed"}]},
  "unresolved_issues": ["尚未完成的具体检查或差异"]
}
```

`verbatim_source` 必须把 `byte_equal` 设为 `true`，并填写实际比较的源哈希；`unchanged_epub` 必须填写原 EPUB 哈希；PDF 必须使用 `pdf_reconstruction` 并填写由 `build_from_ir.py` 产生的覆盖报告路径。每个 evidence 项都必须有 kind、location、result；单独写“已检查”不满足入口校验。

完成后将对应状态写为 `passed`，证据可填写实际报告、已检查位置或截图路径。渲染证据须写明使用的是暂存预览、浏览器、测试构建还是安装版。导入前的暂存预览可支持入库决定；安装版交付检查仍是下一关。

不能用原稿哈希当 EPUB 哈希。最终 EPUB 任何修改后，重新计算哈希并重查受影响项。脚本拒绝旧文件的验收记录，这是为了防止“检查 A，导入 B”。

## 关卡五：只导入检查过的最终 EPUB

```powershell
python <skill-dir>\scripts\persist_epub.py <final.epub> `
  --add-to-library --library "<已核实的 Calibre 书库路径>" `
  --review-report <review.json> --report <import-result.json>
```

导入入口不会重排、改写或合并该文件，也不会新建 Calibre 库。它会校验结构与验收哈希，确认记录实际指向的 EPUB 内容一致。重复导入相同 ZIP 内容应为 `already_present`，ZIP 时间戳不同不应造成重复书。

**不要使用这种绕行方式**：先调用构建脚本把占位/单页种子书入库，然后再把真正排好的文件覆盖进去，以便满足“调用过入库命令”。正确入口已能接受现成最终文件。

替换旧版本时，确认用户授权、准确记录、旧批注/进度、可恢复备份和新旧内容身份。标题相同不足以删除记录。重建改变 DOM 后旧 CFI 可能失效；不得把旧批注静默绑定到新文本。只处理已授权的目标书，不改其他书。

## 关卡六：在用户的软件中验收

1. 刷新安装版书库，读取扫描审计。全部发现的 EPUB 都应成功加载，任何缺失根目录/不可读文件都要说明。
2. 打开刚导入的具体记录，确认标题、作者、路径对应当前版本；不能只看磁盘存在文件。
3. 执行主技能的书籍交付检查：首中尾及复杂内容、Auto/3/4/10 页、单页/整组滑动、跨章节、末尾剩余页、链接、跳转和关闭重开。
4. 确认图与公式没有裁切，长表按完整行、长算法按完整步骤、长图注按段自然续排；短 case 组不被打散。观察实际字体、主题、普通英文行长与窄栏标题是否串入相邻栏。重新打开时从真实章节边界恢复，不能只测书籍第一页。
5. 保留其他书的数据。测试标记/笔记只用隔离样本或本次创建的明确测试项，不能清空用户已有批注。

浏览器预览、复刻前端、模拟 IPC 和测试数据不能证明安装版已经读到书，也不能证明生产进度持久化。截图若捕获了 Codex 或别的窗口，不能把它当成阅读器的证据。

UI 工具失败时按工具恢复流程处理，并继续独立可做的内容检查；不要据此擅自重装程序、改生产标识、覆盖进度文件或把测试库登记进用户书库。确实需要修改应用时，先定位问题属于书还是程序，再按已授权范围处理。

## 最终报告

简洁告诉用户完成状态，详细证据另存报告。至少包括：最终 EPUB/实际库路径、书号、源哈希、实际存储内容核对、公式与插图/表格检查范围、实际打开的软件、测试页数模式、进度恢复，以及未解决问题（若有）。

`draft_not_imported` 是草稿；`awaiting_desktop_verification` 是已入库但未交付验证。不要把精美报告、测试截图或候选文件的存在写成“已经完成”。
